# Production Agent Plugin Implementations: Sentry, Supabase, Axiom, and the Wider Ecosystem

Research date: 2026-08-27. This is a primary-source implementation review of the supplied Sentry, Supabase, Axiom, npm, and Agent Plugins material, plus official implementations from Vercel, Cloudflare, Stripe, PostHog, Neon, GitHub, Convex, and Shopify. Context7 was used to cross-check current documentation; final claims below link to vendor documentation, source repositories, schemas, or published artifacts. This report does not prove live production configuration, runtime traffic, marketplace review, or controls that are not visible in those sources.

This report is a companion to [Agent Plugin Strategy Research](./agent-plugin-strategy.md), which contains the full Agent Plugins 1.0/client comparison and the code-level audit of Taruvi's current MCP server. Here the emphasis is how real products assemble, distribute, secure, test, observe, and evolve their agent integrations.

## Executive decision for Taruvi

The strongest production pattern is not “put every capability in one plugin.” It is a layered product:

1. **Procedural knowledge:** focused Agent Skills and current, retrievable reference material.
2. **Account-bound execution:** a separately operated remote MCP service with OAuth, tenant-aware server policy, bounded tools, and auditable effects.
3. **A portable core plus adapters:** an Agent Plugins 1.0 package for the interoperable `skills/` and `mcp.json` surface, with generated and independently tested Claude, Codex, Cursor, and other client packages where richer behavior is needed.
4. **A release and admission system:** immutable artifacts, provenance, per-client validation, deterministic contract tests, behavioral evals, telemetry disclosure, and rollback.

| Reference implementation | What it demonstrates | Main warning for Taruvi |
| --- | --- | --- |
| **Sentry** | The clearest end-to-end design: one skill source factory, generated Agent Plugins/client packages, a separate hosted MCP service, capability-filtered tool discovery, safety annotations, tests, and MCP evals. | Portable packaging does not establish provenance; rich MCP telemetry can capture sensitive material; installer conflict cleanup is too aggressive to copy. |
| **Supabase** | A practical polyglot distribution repository: shared skills, thin per-client manifests, hosted OAuth MCP, synchronized upstream skill releases, and one release archive. | Its `.plugin/` bundle and the generic `plugins` CLI are **Open Plugin/vendor adapter tooling, not Agent Plugins 1.0**; public validation is incomplete and installer provenance needs scrutiny. |
| **Axiom** | A clean conceptual split between MCP execution and skill methodology, plus persistent operational memory, executable workflows, skill eval infrastructure, agent-created temporary organizations, and identity-level query budgets. | Current official pages contradict each other about read-only behavior and personal-token use; skills can mutate and persist data; the hosted MCP implementation is not established by the deprecated public server repository. |
| **Neon / GitHub / Cloudflare** | Prepare-test-commit mutation protocols, authorization-derived tool discovery, and Code Mode/progressive disclosure for very large APIs. | These controls must be enforced by the execution service, not merely taught in a skill. |
| **Vercel / Stripe / PostHog / Convex / Shopify** | Different combinations of current docs, skills, specialist agents, remote MCP, installers, hooks, runtime feedback, telemetry, and native client packages. | “Plugin” names do not imply format compatibility, safe authority, or equivalent update behavior across clients. |

The immediate Taruvi decision remains: ship `taruvi-engineering` as a private, skills-only package first; harden the MCP authorization and tenancy boundary; then pilot a separate, read-only customer package. The added conclusion from these case studies is that Taruvi should also build a **capability admission broker**, a **server-side action/approval registry**, and **per-release skill/MCP evals** before introducing customer-visible mutations.

## Terminology warning: four different things are called “plugin”

| Name seen in the ecosystem | Identifying shape | Meaning |
| --- | --- | --- |
| **Agent Plugins 1.0.0** | Root `plugin.json` with `$schema: https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`; root `skills/`; optional root `mcp.json` | The vendor-neutral portable floor. Only Skills and MCP servers are portable in v1. |
| **Open Plugin / generic `plugins` CLI format** | Commonly `.plugin/plugin.json`, often with inline `skills`/`mcpServers`, plus translated vendor manifests | A separate multi-client installer/conversion ecosystem. Similar language does not make it Agent Plugins 1.0. |
| **Client-native plugin** | `.claude-plugin/`, `.codex-plugin/`, `.cursor-plugin/`, Gemini/Kimi/Grok/Copilot-specific files | A package interpreted by one client, often with hooks, commands, agents, apps, rules, or other non-portable capabilities. |
| **Product integration bundle** | Any combination of skills, MCP, CLI, hooks, docs, installers, or a marketplace entry | A product/marketing unit; it may use one, several, or none of the formats above. |

Agent Plugins 1.0 deliberately leaves installation, marketplaces, trust, authorization UX, signing, updates, and client extensions outside its portable contract. Format claims must therefore be checked against the actual root manifest and schemas, not inferred from a README or install command. [Agent Plugins specification](https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md), [canonical plugin schema](https://github.com/agentplugins/agent-plugins-spec/blob/main/schemas/1.0.0/plugin.schema.json).

## Case study 1 — Sentry

### Sentry executive assessment

Sentry has deliberately split the product into three layers:

1. A portable, generated **Agent Plugins 1.0.0** package (`getsentry/agent-plugin`) containing a manifest, hydrated Agent Skills, and one hosted Streamable HTTP MCP endpoint.
2. A **source/content factory** (`getsentry/sentry-for-ai`) that owns the skills, shared reference material, per-client transforms, installer, validation, and distribution workflows.
3. A separately implemented **Sentry MCP service** (`getsentry/sentry-mcp`) that owns authentication, authorization, tool discovery/execution, safety metadata, tenancy constraints, rate limiting, telemetry, and actual Sentry API calls. [Sentry plugin documentation](https://docs.sentry.io/ai/agent-plugin/), [portable package](https://github.com/getsentry/agent-plugin/tree/9f9156966be43f1bf4797bd9785a0644bf181d01), [content source](https://github.com/getsentry/sentry-for-ai/tree/ddfc76569bbc649ae0eb4a33018ea895119eed54), [MCP source](https://github.com/getsentry/sentry-mcp/tree/b10d656ca9ee1b1baf5f97d9f3d5991890af2703).

That separation is the key reusable design: a plugin should package context and connection metadata, while the remote service—not prompt instructions or the client UI—enforces identity, scope, tenancy and mutation policy. Sentry's implementation gives a strong pattern for a Taruvi plugin, with two important cautions: its portable package itself carries no trust/provenance mechanism, and its installer performs automatic conflicting-plugin cleanup that Taruvi should not emulate without explicit confirmation. This recommendation is an inference from the implementation and the limits of the portable specification. [Agent Plugins 1.0.0, §§7.2 and 11](https://agent-plugins.org/specification.md#72-mcp-servers), [Sentry installer cleanup behavior](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/packages/installer/src/harnesses/codex.ts#L13-L18).

### 1. The portable package and Agent Plugins 1.0.0 conformance

**Confirmed.** The generated package root contains `plugin.json`, `mcp.json`, `skills/`, `README.md`, and `LICENSE`. Its manifest declares Agent Plugins schema `1.0.0`, name `sentry`, version `1.3.2`, standard metadata, and no non-standard manifest fields. Its `mcp.json` declares a single `sentry` server using `streamable-http` at `https://mcp.sentry.dev/mcp?utm_source=plugin`. [Package manifest](https://github.com/getsentry/agent-plugin/blob/9f9156966be43f1bf4797bd9785a0644bf181d01/plugin.json), [package MCP configuration](https://github.com/getsentry/agent-plugin/blob/9f9156966be43f1bf4797bd9785a0644bf181d01/mcp.json).

**Confirmed.** This directly matches the v1 portable layout: root `plugin.json`; immediate `skills/<name>/SKILL.md` discovery; root `mcp.json`; and the `streamable-http` transport. The specification requires the two schema identifiers to match, permits a remote HTTPS MCP URL, and explicitly says portable v1 has only Skills and MCP-server components. [Agent Plugins 1.0.0, §§4–7](https://agent-plugins.org/specification.md#4-plugin-package-model), [MCP schema](https://agent-plugins.org/schemas/1.0.0/mcp.schema.json).

**Source-code inference.** Sentry's portable package is statically conformant with the relevant package-shape and schema-version requirements. This is not a certification that every compatible client loads it identically: Agent Plugins intentionally leaves distribution, installation, authorization UI, credential storage, and client-specific behavior to the client. [Agent Plugins 1.0.0, §§7.2.1, 8, and 11](https://agent-plugins.org/specification.md#721-discovery-and-configuration).

**Confirmed.** Sentry's source build validates the generated Agent Plugin by checking the published plugin and MCP schemas, root containment, and basic Agent Skill frontmatter/name/body requirements. That is a useful producer-side gate; client-side containment and loading behavior remain a client responsibility under the specification. [Agent Plugin validator](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/src/plugins/agent-plugin/validate.sh), [Agent Plugins containment rules](https://agent-plugins.org/specification.md#41-general-requirements).

### 2. Content factory: skills, references, and client adaptation

**Confirmed.** `sentry-for-ai` describes itself as a source repository rather than an installation target. It builds five generated distribution shapes—portable Agent Plugin, Claude Code, Cursor, Codex, and Grok—from one skill/reference source, and the source README identifies the destination repositories. [Source-repository statement and distribution table](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/README.md#L3-L14), [build/distribution design](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/README.md#L67-L104).

**Confirmed.** The active skill tree includes onboarding, instrumentation, issue debugging, stack-trace remediation, alert creation, OpenTelemetry exporter setup, release setup, and Cocoa snapshot setup. Skills use `SKILL.md`; a `references.yml` declaration lets the common build hydrate shared references into each shipped skill, leaving the result self-contained. [Skill tree](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/src/SKILL_TREE.md), [source README on reference hydration](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/README.md#L130-L139), [common build functions](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/scripts/build-common.sh#L30-L113).

**Confirmed.** Per-client artifacts are not a blind copy. The Codex build emits a package under `plugins/sentry`, translates the portable `mcp.json` into Codex's `.mcp.json`, hydrates the skills, and turns source `disable-model-invocation: true` metadata into Codex `agents/openai.yaml` files with `policy.allow_implicit_invocation: false`; the build then validates using a pinned OpenAI validator. [Codex build](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/src/plugins/codex/build.sh), [Codex hidden-skill transform](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/src/plugins/codex/hide-skills.py), [Codex validation](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/src/plugins/codex/validate.sh).

**Reusable pattern for Taruvi.** Keep an immutable source-of-truth tree for portable skills and reference content, generate each client target, and run that target's own validator in release CI. Treat client behavior—particularly whether a skill can be auto-invoked—as an adapter concern, not a claim made in a portable `SKILL.md`. This is a recommendation derived from Sentry's build structure and Agent Plugins' fixed portable surface. [Sentry client builds](https://github.com/getsentry/sentry-for-ai/tree/ddfc76569bbc649ae0eb4a33018ea895119eed54/src/plugins), [Agent Plugins component model](https://agent-plugins.org/specification.md#7-component-types).

### 3. MCP architecture and the relationship between the repositories

**Confirmed.** `sentry-for-ai` only configures the hosted MCP endpoint; it does not vendor the MCP implementation. The public plugin documentation says installation configures Sentry MCP automatically, while the content-source MCP file points at the hosted endpoint. The server's tool/auth/runtime behavior therefore belongs to `sentry-mcp`, not to the portable plugin. [Plugin documentation](https://docs.sentry.io/ai/agent-plugin/), [content-source `mcp.json`](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/mcp.json), [MCP repository](https://github.com/getsentry/sentry-mcp/tree/b10d656ca9ee1b1baf5f97d9f3d5991890af2703).

**Confirmed.** The MCP codebase is a TypeScript/pnpm monorepo with a reusable core, a Node stdio server, a Cloudflare hosted server, deterministic mocks, a test client, smoke tests, and an eval package. Its root scripts expose build, typecheck, lint, unit tests, evals, and CI variants. [Repository package layout](https://github.com/getsentry/sentry-mcp/tree/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages), [root scripts](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/package.json).

**Confirmed.** The hosted Cloudflare route constructs a fresh MCP SDK v2 server for each authenticated request, capturing request-specific authentication, granted skills, organization/project constraints, client family and transport in the server context. It uses a Streamable HTTP MCP handler; it separately supports a Node stdio transport for local process use. [Hosted request handler](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-cloudflare/src/server/lib/mcp-handler.ts), [core server builder](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/server.ts), [stdio transport](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-server/src/transports/stdio.ts).

**Source-code inference.** The architecture makes the same tool catalogue portable across hosted and local modes while keeping the deployed HTTP service as the control point for OAuth, constraints and rate limits. The present source does not establish that every deployment mode has the same policy configuration or feature flags.

### 4. Authentication, authorization, and tenant constraints

**Confirmed.** The hosted MCP server is wrapped by an OAuth provider and exposes protected-resource/authorization-server discovery metadata. It accepts both the OAuth-mediated path and a distinct `Sentry-Bearer` direct-token path. The direct path deliberately bypasses server-side token validation, storage, refresh and revocation; it supplies the token to the Sentry API context. [Hosted app routes](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-cloudflare/src/server/app.ts), [direct-token and OAuth handling](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-cloudflare/src/server/lib/mcp-handler.ts).

**Important exception.** `Sentry-Bearer` is a custom direct-upstream-token mode, not a reusable MCP OAuth bearer-token pattern. Taruvi should not copy it: the MCP authorization specification requires an MCP server to validate that an access token was issued for itself and forbids accepting or transiting a token intended for another resource. [MCP authorization token-audience rules](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization#access-token-usage-and-security)

**Confirmed.** Server authorization is capability-oriented. Skills such as `inspect` and `seer` default on, while `triage` and `project-management` default off; each tool declares eligible skills, and the core filters the registered/discoverable tools to the session's grants. Hosted OAuth consent only offers active, non-deprecated skills. [Skill registry](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/skills.ts), [availability filtering](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/tools/catalog-runtime/availability.ts), [approval-dialog policy](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-cloudflare/src/server/lib/approval-dialog.ts).

**Confirmed.** The hosted handler parses optional organization/project path constraints, rejects requests that conflict with token constraints, verifies OAuth users' access to requested constraints, injects those constraints into tool schemas/arguments, and rate-limits by user or direct-token identifier. [Constraint and rate-limit path](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-cloudflare/src/server/lib/mcp-handler.ts), [schema filtering/injection](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/tools/catalog-runtime/availability.ts).

**Confirmed.** The stdio server can fall back to OAuth device-code authorization when targeting `sentry.io` without an access token, and caches credentials in `~/.sentry/mcp.json` with a `0700` parent directory, `0600` atomic file writes, and early-expiry eviction. [Node entry point](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-server/src/index.ts), [device code flow](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-server/src/auth/device-code-flow.ts), [token cache](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-server/src/auth/token-cache.ts).

**Reusable pattern for Taruvi.** Separate read, investigation, and mutation grants; bind every request to authenticated Taruvi identity and tenant/project scope server-side; filter both tool *discovery* and *execution* by that context; and use short-lived, revocable credentials. Never treat the portable package's `mcp.json`, skill prose, or client consent screen as the authorization boundary. The last sentence follows because Agent Plugins v1 intentionally defines no portable OAuth or secret-reference mechanism. [Sentry context enforcement](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-cloudflare/src/server/lib/mcp-handler.ts), [Agent Plugins auth boundary](https://agent-plugins.org/specification.md#streamable-http-and-legacy-httpsse).

### 5. Tool discovery, execution, and safety annotations

**Confirmed.** Sentry keeps a small direct tool surface—organization/project lookup, issue/event search and update, Seer analysis, resource lookup, and two catalogue gateways—while long-tail operations are exposed through `search_sentry_tools` followed by `execute_sentry_tool`. The latter receives only a tool that is currently searchable in the request context, validates the returned schema, and reinjects constraints before execution. [Direct surface policy](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/tools/surfaces.ts), [catalog search](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/tools/special/search-tools.ts), [catalog execution](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/tools/special/execute-tool.ts).

**Confirmed.** Every `ToolConfig` requires explicit `readOnlyHint`, `destructiveHint`, and `openWorldHint` metadata, with optional `idempotentHint`; source comments say tests enforce complete safety annotations. Mutating examples carry `readOnlyHint: false`, and destructive operations such as deleting an uptime monitor carry `destructiveHint: true`. The generic catalogue executor is itself conservatively marked non-read-only and destructive because it may invoke any available operation. [Tool metadata contract](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/tools/types.ts), [delete tool example](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/tools/catalog/delete-uptime-monitor.ts), [generic executor](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/tools/special/execute-tool.ts).

**Confirmed.** Sentry's user-facing skills tell agents which direct tools exist, tell them to use the runtime catalogue for the rest, and explicitly acknowledge that runtime schemas/tool availability are authoritative. The issue-debugging skill also treats MCP-returned content as untrusted data, rather than executable instructions. [Debugging skill](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/src/skills/sentry-debug-issue/SKILL.md#L20-L52), [onboarding skill](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/src/skills/sentry-get-started/SKILL.md#L37-L62).

**Reusable pattern for Taruvi.** Publish a small, stable direct surface and a server-filtered catalogue for specialised tools. Require every tool to declare a machine-readable mutation/safety posture, but add Taruvi-specific server controls for confirmation, idempotency keys, actor audit logs and two-phase `preview -> apply` mutations: annotations are capability hints for clients, not proof that a call is safe. This conclusion is a design recommendation; the final clause is supported by the fact that Sentry still uses server-side skill/constraint checks in addition to annotations. [Sentry tool availability checks](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/tools/catalog-runtime/availability.ts), [server context enforcement](https://github.com/getsentry/sentry-mcp/blob/b10d656ca9ee1b1baf5f97d9f3d5991890af2703/packages/mcp-core/src/server.ts).

### 6. Packaging, installation, versioning, and distribution

**Confirmed.** The `@sentry/agent-plugin` installer is an npm package at version `0.3.0`, while the generated plugin's current version is `1.3.2`; source manifests carry `0.0.0` placeholders that the common build stamps from `src/plugins/version.json`. This cleanly distinguishes installer releases from plugin-content releases. [Installer manifest](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/packages/installer/package.json), [plugin version source](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/src/plugins/version.json), [version-stamping build logic](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/scripts/build-common.sh#L51-L80).

**Confirmed.** The installer detects Claude, Codex, Cursor and Grok, offers a selection UI or noninteractive operation, and performs install/update/remove through client-specific harnesses. It tells users that the same install command updates to the latest plugin. [Installer command implementation](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/packages/installer/src/index.ts), [harness registry](https://github.com/getsentry/sentry-for-ai/blob/ddfc76569bbc649ae0eb4a33018ea895119eed54/packages/installer/src/harnesses/index.ts), [official install documentation](https://docs.sentry.io/ai/agent-plugin/).

**Confirmed.** A material caveat is that several harnesses remove a competing Sentry plugin before installing their preferred one; the Codex harness explicitly removes `sentry@openai-curated` because it considers it shadowing. Removal of Sentry's own installed plugin is narrower, leaving the marketplace registration in place. ## Case study 2 — Supabase and the generic `plugins` installer

### 1. Product architecture and distribution

**Confirmed at the reviewed distribution snapshot.** Supabase documents one plugin bundle containing its hosted MCP server and two skills, installed with `npx plugins add supabase-community/supabase-plugin`. The public distribution repository contains a shared root `skills/` tree plus client adapters for Claude, Cursor, Codex, Grok, Kimi, GitHub/Copilot, Gemini, and a generic `.plugin/` format. The Codex adapter refers to a registered Codex app, while most other adapters point to `https://mcp.supabase.com/mcp` and add non-secret source/version headers. [Supabase plugin documentation](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/ai-tools/plugins.mdx), [distribution snapshot](https://github.com/supabase-community/supabase-plugin/tree/8629243d1cd72309b533090a4c742f21747d02fa), [Codex manifest](https://github.com/supabase-community/supabase-plugin/blob/8629243d1cd72309b533090a4c742f21747d02fa/.codex-plugin/plugin.json), [Codex app adapter](https://github.com/supabase-community/supabase-plugin/blob/8629243d1cd72309b533090a4c742f21747d02fa/agents/codex/.app.json).

**Confirmed.** Skill content is maintained separately in `supabase/agent-skills`. Its release workflow produces artifacts and an index; the distribution repository's sync workflow downloads each release artifact and verifies its SHA-256 digest before extraction. This is a useful “content source -> verified adapter repository” model, though it verifies the transferred skill artifact rather than establishing end-to-end publisher/build provenance for the final plugin release. [Agent-skills release workflow](https://github.com/supabase/agent-skills/blob/8331f910845103c08d51f6ca1d86ebb7d1f745e3/.github/workflows/release.yml), [plugin synchronization workflow](https://github.com/supabase-community/supabase-plugin/blob/8629243d1cd72309b533090a4c742f21747d02fa/.github/workflows/sync-agent-skills.yml).

The two shipped skills at that snapshot have intentionally different responsibilities: a broad Supabase product workflow skill and a Postgres best-practices skill. The product skill directs the agent to current documentation/changelog evidence, OAuth-based MCP setup, migration discipline, and security checks; the database skill progressively loads detailed references. This is preferable to one huge always-loaded instruction file. ### 2. It is not currently an Agent Plugins 1.0 package

| Agent Plugins 1.0 requirement | Current Supabase distribution | Result |
| --- | --- | --- |
| Root `plugin.json` with required canonical `$schema` and `name` | No root `plugin.json`; generic manifest is `.plugin/plugin.json` | Not conformant |
| Closed portable manifest fields | Generic manifest adds inline `skills` and `mcpServers` | Invalid under the Agent Plugins 1.0 root schema |

This distinction matters operationally: Supabase's bundle is a good multi-client **adapter product**, but it is not evidence that the generic installer validates or installs the Agent Plugins 1.0 contract. Taruvi should add a real conforming root package if it wants the portable standard, while retaining native adapters for richer client behavior. ### 3. Authentication and production safety

**Confirmed.** Supabase's remote MCP uses browser authorization/dynamic client registration by default; a PAT can be supplied for clients or CI that cannot complete browser OAuth. The plugin manifests contain endpoints and attribution headers, not embedded credentials. Supabase explicitly warns against connecting the MCP server to production data, calls out prompt injection, recommends manual tool-call approval, and provides narrowing controls such as `read_only`, `project_ref`, and feature groups. [MCP authentication](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/ai-tools/mcp.mdx#L125-L162), [security risks and mitigations](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/ai-tools/mcp.mdx#L164-L194).

**Taruvi implication.** Supabase's warnings are useful defaults, but a customer-facing Taruvi service cannot rely on “do not use production” or manual approvals alone. Tenant/app scope, read-only enforcement, feature grants, confirmation, and audit must be authenticated server properties. A plugin package should contain no Knox token, Infisical value, Stripe key, database credential, or other secret.

### 4. What `plugins@1.3.4` actually establishes

The unscoped npm package `plugins` is a generic Node 18+ CLI for detecting several installed agent clients, cloning a Git or local source, discovering vendor/Open Plugin layouts, and invoking target-specific installation paths. Its documented commands are `add`, `discover`, and `targets`; there is no dedicated `update` command. Re-running `add` rebuilds a fresh staging/cache result, while final update behavior remains client-specific. [npm package page](https://www.npmjs.com/package/plugins), [published npm metadata](https://registry.npmjs.org/plugins/1.3.4), [published tarball](https://registry.npmjs.org/plugins/-/plugins-1.3.4.tgz).

The published `1.3.4` artifact's discovery rules look for `.plugin/plugin.json`, several client-native manifests, marketplaces, and component folders within a shallow scan. They do not make the CLI an Agent Plugins 1.0 validator. For Codex, the bundle transforms/registers a cached native package; its `scope` value is accepted but does not create a truly project-isolated Codex install. The Taruvi-safe usage posture is therefore: run discovery first, name one explicit target, inspect the source and release, and do not infer scope or conformance from the CLI's success.

**Supply-chain finding.** npm metadata names account `quuu` as publisher/maintainer and declares `https://github.com/vercel-labs/plugins` as its repository. That public repository URL returned 404 during this review, and the npm release did not present a public provenance attestation. The artifact also sends opt-out install telemetry to a `labs.vercel.dev` endpoint, including source, discovered plugin names/count, installed target IDs, scope, CLI version, and CI status; a local source string can therefore expose a path. `DISABLE_TELEMETRY` or `DO_NOT_TRACK` disables it. The bundle's telemetry initializer says `1.2.8` while the package metadata says `1.3.4`; the reason is unknown. These facts do **not** prove Supabase ownership or Vercel corporate ownership of the package. They are reasons to pin, review, and attest the installer used for Taruvi releases. [npm metadata](https://registry.npmjs.org/plugins/1.3.4), [declared but unavailable repository](https://github.com/vercel-labs/plugins).

### 5. Test and release gaps

**Confirmed at the reviewed snapshots.** Supabase's distribution CI validates the Claude manifest and a Grok plugin path, while contributor guidance asks maintainers to test affected clients manually. The skill repository has Vitest installation-sanity checks. Release Please propagates a common distribution version into manifests and attribution headers, and a release workflow produces an archive. No public model-behavior eval suite or full matrix proving every shipped client adapter was found. [Manifest validation workflow](https://github.com/supabase-community/supabase-plugin/blob/8629243d1cd72309b533090a4c742f21747d02fa/.github/workflows/validate-plugin-manifests.yml), [contributor test guidance](https://github.com/supabase-community/supabase-plugin/blob/8629243d1cd72309b533090a4c742f21747d02fa/CONTRIBUTING.md), [skill sanity test](https://github.com/supabase/agent-skills/blob/8331f910845103c08d51f6ca1d86ebb7d1f745e3/test/sanity.test.ts), [release workflow](https://github.com/supabase-community/supabase-plugin/blob/8629243d1cd72309b533090a4c742f21747d02fa/.github/workflows/release.yml).

## Case study 3 — Axiom

### 1. Complementary MCP and Skills planes

**Confirmed.** Axiom explicitly presents two complementary integrations. Its hosted MCP is browser-OAuth based and loads tool definitions up front; its Skills use configured API tokens, load on demand, and add investigation methodology and memory. Axiom recommends using both: MCP for query execution and Skills for structured investigation/learning. [Axiom AI agents overview](https://axiom.co/docs/console/intelligence/ai-agents-overview), [Axiom Skills](https://axiom.co/docs/console/intelligence/skills), [Axiom MCP](https://axiom.co/docs/console/intelligence/mcp-server).

The hosted server documents a broad tool set and six investigation prompts; MCP resources are planned rather than currently supported. This is a useful separation: repeatable model-facing investigation recipes can be prompts or skills, while live product data and effects remain tools. Taruvi should still prefer portable Skills for cross-client procedures because MCP prompts are server/client behavior rather than an Agent Plugins v1 portable component. [Axiom MCP capabilities](https://axiom.co/docs/console/intelligence/mcp-server#current-capabilities).

This separation is conceptually strong for Taruvi. Product/API facts, investigation procedures, and repository-specific checks belong in Skills; identity-bearing reads and effects belong behind the remote execution boundary. The two layers should share one capability vocabulary, but the skill must not be allowed to expand the server's authority.

### 2. Current documentation contains two material contradictions

**Read-only contradiction.** The overview calls the hosted MCP's operations “curated, read-only” and says there is no destructive-action risk. The current MCP capability page lists `create*`, `update*`, and `delete*` tools for dashboards, monitors, and notifiers. Until Axiom corrects or scopes those statements, the actual `tools/list`, server authorization, and client approvals are authoritative—not the overview wording. [Read-only claim](https://axiom.co/docs/console/intelligence/ai-agents-overview), [current MCP tools](https://axiom.co/docs/console/intelligence/mcp-server#current-capabilities).

**Token contradiction.** Axiom's token-hygiene guidance says never use a personal access token for an AI agent because it has full account control. The same MCP setup page instructs clients without browser OAuth to send a personal access token and organization ID in headers. This is a high-risk fallback and should not be copied into Taruvi documentation. Taruvi should offer proper OAuth/device authorization or a dedicated app token with exact audience, tenant, app, action, expiry, and revocation semantics. [Token hygiene](https://axiom.co/docs/console/intelligence/ai-agents-overview#token-hygiene-for-ai-agents), [header authentication](https://axiom.co/docs/console/intelligence/mcp-server#header-based-authentication).

**Source boundary.** The public Go `mcp-server-axiom`/`axiom-mcp` repository is marked deprecated and contains an older six-tool, token-authenticated, read-oriented server without the hosted service's documented prompts and mutation surface. The hosted implementation, safety annotations, authorization details, and production telemetry cannot be inferred from that old repository. [Deprecated MCP repository](https://github.com/axiomhq/mcp-server-axiom).

**Residency and public-source boundary.** Axiom states that hosted-MCP query results route through US infrastructure, including for organizations whose event data is on its EU edge. The reviewed Skills MCP adapter identifies `github.com/axiomhq/mcp` as the hosted server source, but that repository was not publicly resolvable during this review. The hosted service revision, OAuth-to-RBAC mapping, tool-side authorization checks, result retention, telemetry, and exact residency handling are therefore unknown from public source. Taruvi should not route production or EU-resident telemetry through it until those points are accepted explicitly. [Hosted result routing](https://axiom.co/docs/console/intelligence/mcp-server#query-results-routing), [Axiom edge deployments](https://axiom.co/docs/reference/edge-deployments), [reviewed Skills MCP adapter](https://github.com/axiomhq/skills/blob/7f29f9a97ffd71bf2ad375e035ba6f3ba30dcc8b/.mcp.json).

### 3. Skills are executable operational products, not passive documentation

At commit `7f29f9a9…`, the public `axiomhq/skills` repository includes SRE investigation, alerting, dashboards, cost control, metrics, SPL translation, chart rendering, and eval-authoring skills. The bundle configures the hosted MCP for compatible plugin clients, but it has `.mcp.json` and a Grok manifest rather than a conforming Agent Plugins 1.0 root manifest. [Axiom Skills snapshot](https://github.com/axiomhq/skills/tree/7f29f9a97ffd71bf2ad375e035ba6f3ba30dcc8b), [skills inventory](https://github.com/axiomhq/skills/blob/7f29f9a97ffd71bf2ad375e035ba6f3ba30dcc8b/README.md), [MCP adapter](https://github.com/axiomhq/skills/blob/7f29f9a97ffd71bf2ad375e035ba6f3ba30dcc8b/.mcp.json).

That snapshot includes more than 100 scripts across query, dashboard, alert, Slack, Grafana, Pyroscope, Sentry, configuration, and memory workflows. Some create, update, or delete product objects. This explains Axiom's “flexible beyond curated tools” claim, but it also means installation introduces executable artifacts that can run if host/client policy, approval, sandboxing, and the configured API token allow it. Taruvi should classify skill scripts as code requiring artifact admission, sandboxing, egress/file restrictions, and explicit mutation policy—not as harmless Markdown.

The reviewed Skills snapshot had no tagged/released immutable distribution; the documented install fetches repository content. Adopters should pin a reviewed commit or internal artifact rather than treating moving `main` as a production dependency. The hosted MCP deployment/version lifecycle is not public. [Axiom Skills snapshot](https://github.com/axiomhq/skills/tree/7f29f9a97ffd71bf2ad375e035ba6f3ba30dcc8b).

The SRE skill's persistent memory is distinctive: personal memory is local, organization memory may be Git-synchronized, successful investigations can be written automatically, and consolidation can commit/push shared memory. This can improve incident response, but it creates retention, poisoning, privacy, provenance, and cross-tenant risks. Taruvi should use typed, provenance-tagged, tenant-partitioned evidence with review/expiry rather than unconstrained Markdown auto-learning. [SRE skill](https://github.com/axiomhq/skills/blob/7f29f9a97ffd71bf2ad375e035ba6f3ba30dcc8b/skills/sre/SKILL.md), [memory system](https://github.com/axiomhq/skills/blob/7f29f9a97ffd71bf2ad375e035ba6f3ba30dcc8b/skills/sre/reference/memory-system.md).

### 4. Evals: a useful shape with narrower current coverage than the framework suggests

Axiom has a changed-skill evaluation workflow, stored baselines, PR result comments, and two harness modes: one injects the entire skill/reference set into the system prompt; the other simulates progressive discovery through a `skill` tool plus bounded reference reads. The latter directly tests whether a model discovers the skill and follows its reference-loading instructions while measuring tokens, latency, and tools called. [Changed-skill workflow](https://github.com/axiomhq/skills/blob/7f29f9a97ffd71bf2ad375e035ba6f3ba30dcc8b/.github/workflows/eval-changed-skills.yml), [tool-simulation harness](https://github.com/axiomhq/skills/blob/7f29f9a97ffd71bf2ad375e035ba6f3ba30dcc8b/eval-tooling/src/harnesses/tool-simulation.ts), [full-content harness](https://github.com/axiomhq/skills/blob/7f29f9a97ffd71bf2ad375e035ba6f3ba30dcc8b/eval-tooling/src/harnesses/prompt-injection.ts).

Important naming caveat: the source calls the full-content harness `prompt-injection`, meaning “inject the skill into the prompt”; it is **not** evidence of an adversarial prompt-injection security suite. At the reviewed `7f29f9a9…` snapshot, only `spl-to-apl` had a tracked `.meta/*.eval.ts` and stored baseline. Taruvi should reuse the comparative harness design, but extend it across every public skill and add hostile retrieved-data, cross-tenant, secret-redaction, unsafe-mutation, and misleading-tool-annotation cases.

Both public harnesses call a named external model through Axiom's AI SDK/gateway. The reviewed public sources do not establish retention and processing terms for every eval prompt/output path. Taruvi evals must use synthetic data by default and pass the same privacy/residency review as production telemetry. [Axiom eval harness](https://github.com/axiomhq/skills/blob/7f29f9a97ffd71bf2ad375e035ba6f3ba30dcc8b/eval-tooling/src/harnesses/tool-simulation.ts).

### 5. Agent onboarding and cost governance

**Agent-created organizations.** Axiom exposes a public unauthenticated provisioning endpoint that returns a real temporary organization, a one-time claim URL, and a full-permission token. Unclaimed organizations expire after 24 hours, are limited to three per day and reduced ingest/query budgets, and are permanently deleted if not claimed. This is an innovative zero-friction trial—not a sandbox—and both returned values are secrets. Production Taruvi agents should not be allowed to call that external provisioning route or log/retain its returned secrets. Taruvi should consider claimable, short-lived **synthetic demo tenants** only if they are isolated from production, carry no existing customer data, use sharply bounded credentials, and have deterministic expiry/abuse controls. [Agent-created organizations](https://axiom.co/docs/console/intelligence/agent-created-orgs).

**Identity budgets.** Axiom lets operators place hourly/daily query-cost limits on API tokens and roles; exhausted identities receive `429` until reset, while other operations continue. OAuth sessions act as the member and inherit role limits. This is a strong pattern for Taruvi: add per-tenant, per-actor, per-plugin-digest, and per-capability budgets for query volume, compute, output bytes, tool calls, and billable external operations. Budget enforcement must cover mutations separately because Axiom's documented query cap does not block management operations. [Query-cost limits](https://axiom.co/docs/console/intelligence/query-cost-limits).

## Cross-product production checklist for Taruvi

### 1. Package trust and client adaptation

- Treat `plugin.json` as format metadata, not publisher identity or provenance. Admit a release only by immutable digest, approved publisher/source, reproducible build evidence, SBOM, signature/attestation, and review of executable scripts/hooks/remote origins. [SLSA artifact verification](https://slsa.dev/spec/v1.2/verifying-artifacts)
- Maintain one normalized Taruvi capability model and generate AP1, Claude, Codex, Cursor, and other adapters from it. Client extensions never receive implicit authority merely because a client understands them.
- Validate the **extracted final artifact** and install it in clean client environments. Pin validator versions and archive the results with the release.
- Keep updates explicit and reversible. A new plugin digest, remote origin, scope, hook, script, or `tools/list` entry is a security-relevant change requiring diff, canary, and possibly renewed approval.

### 2. Remote MCP authorization and tenancy

- **MCP server duties:** publish protected-resource metadata, validate that every presented access token is audience-bound to that MCP server, and never accept or transit a token intended for an upstream resource. [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
- **Authorization-server duties:** implement the specified OAuth 2.1 profile, publish OAuth/OIDC discovery metadata, use HTTPS, and validate redirect URIs exactly. The MCP specification says authorization servers **should** issue short-lived access tokens and **must** rotate refresh tokens for public clients. [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
- **MCP client duties:** discover the resource and authorization-server metadata, send the RFC 8707 `resource` parameter in authorization and token requests, implement PKCE, use `S256` when capable, and use and verify `state` as the specification recommends. [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)
- **Taruvi's stricter policy:** require `state`, strict audience validation, short-lived access tokens, and refresh-token rotation wherever refresh tokens are issued, including where the base specification only says **should**. [MCP security guidance](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices)
- Derive actor, tenant, app, role, environment, and effective capability from validated server context. Never accept tenant authority from a tool argument, skill, model output, free-form header, or client-side approval alone.
- Filter `tools/list`, catalogue search, and execution with the same policy. A model should not see tools it cannot invoke. Reauthorize every call and every apply step; annotations are user-interface hints, not policy.
- Separate read, export, write, delete, credential, billing, identity, and administrator capability grants. Use distinct public read-only and private operator endpoints/packages where the trust boundaries differ.

### 3. Consequence-aware execution

- Make important mutations two-phase: `prepare/preview -> validate/test -> apply/commit`. Return an opaque expiring plan token/hash; bind approval to the normalized arguments, actor, tenant, plugin digest, target set, and expiry; re-check drift and authorization on apply.
- Require idempotency keys, bounded target counts, clear side-effect summaries, audit events, cancellation behavior, and safe retry semantics.
- For very broad APIs, expose a small direct surface plus server-filtered discovery, or use a sandboxed Code Mode approach with narrow credentials, egress policy, CPU/memory/time limits, and a restricted generated SDK.
- Treat local skill scripts and stdio MCP servers as code. Default-deny inherited credentials, filesystem writes, and network access; give them a dedicated writable data directory and explicit capability grants.

### 4. Progressive disclosure and context economics

- Load only skill name/description at session start; load `SKILL.md` after activation; fetch references/assets/scripts only when needed. Keep the main skill concise and route current facts to authoritative retrievable docs. [Agent Skills specification](https://github.com/agentskills/agentskills/blob/main/docs/specification.mdx)
- Cap tool-result bytes, rows, time ranges, query complexity, and pagination. Return structured summaries plus cursors/links instead of raw unbounded data.
- Add Axiom-style per-identity budgets and extend them to per tenant, plugin digest, capability, external billable service, tool calls, output bytes, and concurrency. A query budget alone does not constrain mutations.

### 5. Tests, evals, and drift control

Use separate release gates for:

1. schema, containment, archive determinism, secret scanning, provenance, and client-manifest validation;
2. MCP initialization, OAuth, audience/scope, `tools/list`, annotations, cancellation, timeouts, paging, and redaction;
3. authorization parity, wrong-tenant/wrong-app substitution, field/row restrictions, replayed/stale plans, prompt injection in retrieved data, SSRF, and tool-surface drift;
4. skill activation/non-activation, reference discovery, outcome quality, tool selection, context/latency/cost budgets, and safe refusal;
5. clean install, update, disable, rollback, uninstall, and client restart behavior on each supported host.

Sentry demonstrates distinct installer and MCP eval suites; Axiom demonstrates full-content versus progressive-discovery skill harnesses; Neon demonstrates layered protocol/browser E2E. Taruvi should combine all three and run them against synthetic tenants with seeded cross-tenant canaries.

### 6. Telemetry, privacy, and audit

- Publish a field-level telemetry contract before installation: destination, purpose, retention, sampling, fields, defaults, opt-out, and how to inspect/delete local identifiers.
- Default to metadata-only product metrics. Do not record raw prompts, tool arguments/results, source code, SQL, secret values, customer rows, PII, stack traces containing credentials, or local paths.
- Keep security audit evidence separate from product analytics. Audit should record pseudonymous actor/tenant, plugin digest/version, client adapter, action class, authorization verdict, approval/plan ID, result code, latency, budget usage, and rollback status.
- Redaction is defense in depth, not permission to collect everything. Test canary-secret leakage across logs, traces, errors, eval artifacts, analytics, and support exports. [OpenAI tracing privacy controls](https://openai.github.io/openai-agents-python/tracing/)

## New Taruvi strategies derived from the case studies

### 1. Plugin admission broker

Do not let production users or CI execute an arbitrary moving Git repository directly. A Taruvi admission service should resolve a requested release, verify publisher/source/provenance, unpack and validate it, enumerate scripts/hooks/origins/capabilities, scan secrets, assign an immutable digest, run the appropriate client/MCP/eval suite, and issue an installation record. Installation and runtime authorization remain separate decisions.

### 2. One-time capability leases

Before a consequential operation, mint a short-lived, single-use server lease bound to `{actor, tenant, app, plugin_digest, tool_id, normalized_arguments_hash, approval_id}`. The execution plane rejects replay, substitution, wrong-tenant use, changed policy, or changed targets. This strengthens the existing recommended preview/apply design into a concrete server primitive.

### 3. Generated capability contract

Maintain one reviewed machine-readable registry for every Taruvi agent capability: tool schema, domain action, required scope, tenancy key, data class, mutation/destructive/open-world/idempotent posture, target limits, confirmation class, audit event, rate/cost budget, owning service, and tests. Generate MCP registration, `tools/list` assertions, OAuth consent text, documentation, plugin risk inventory, and parity tests from it. This directly addresses the current risk of tool prose, middleware, Cerbos, docs, and implementation drifting independently.

### 4. Tenant-safe evaluation lab

Each candidate plugin/MCP release should run against multiple synthetic tenants containing unique canary records and secrets. Promotion fails if any workflow reaches another tenant, returns a canary outside its tenant, invokes an unreviewed tool, bypasses preview/apply, leaks a seeded secret into telemetry, or exceeds budget. Retain the exact model/client/tool versions and release digest with each result.

### 5. Evidence memory instead of unrestricted agent memory

Axiom shows the value of incident memory but also its risks. Taruvi should store learned operational evidence as typed records with tenant/environment, source query or event link, actor, timestamp, confidence, expiry, visibility, supersession, and review status. Never allow an agent to auto-push shared memory across tenants or treat remembered text as current truth without live verification.

### 6. Claimable demo environments, only after isolation exists

Axiom and Neon show that claimable temporary environments can remove onboarding friction. For Taruvi, this should mean an isolated, synthetic, expiring demo tenant with no production connectivity, bounded resources/actions, one-time claim transfer, and abuse controls—not an automatically provisioned normal tenant with broad platform credentials.

## Final assessment

Sentry is the best overall architectural reference; Supabase is the clearest example of a pragmatic multi-client adapter repository; Axiom contributes the strongest ideas around methodology, operational memory, ephemeral onboarding, and cost budgets—but also the clearest warning that product documentation can drift from the true mutation/authentication surface.

For Taruvi, the winning product is not a universal plugin with 24 broad tools. It is a small, portable instruction core; separately generated client adapters; a remote, tenant-aware execution service with policy-derived discovery; and an admission/evaluation/observability system that treats every package, tool, script, update, and remembered fact as untrusted until verified. The existing MCP can become that backend only after its current authorization, app scoping, destructive-operation, credential, annotation, Origin, parity, audit, and test gaps are closed as documented in the companion report.
